# 01 — monorepo-scaffold

## Item

Repository, workspace tooling, and the two applications.

## Source

PRD §20 (foundation phase). Layout fixed by `ARCHITECTURE.md` §3.

## Goal

A pnpm workspace containing a NestJS API and a Next.js web application, both building,
testing, linting, and type-checking from the repository root, with the shared packages
wired and proven across the boundary.

## Approach

1. Scaffold `apps/api` with the Nest CLI and `apps/web` with `create-next-app`. — done
2. Establish the pnpm workspace; remove the nested `pnpm-workspace.yaml` that
   `create-next-app` writes into `apps/web`. — done
3. Add `packages/domain` and `packages/contracts` per Decisions 3.1 and 3.2. — done
4. Align the toolchain: one TypeScript version, shared `tsconfig.base.json`, root
   Prettier configuration. — done
5. Give the API its `/api/v1` prefix (Decision 11.1), typed environment loading, and the
   health endpoint required by PRD §12.3. — done
6. Apply the brand tokens from `DESIGN.md` and prove a cross-package import renders. — done
7. Verify build, test, typecheck, and lint from the root. — done
8. Replace the Commands placeholder in `CLAUDE.md`. — done

## Decisions taken during execution

Recorded here because they were left open at `ARCHITECTURE.md` §14.

| Matter | Decision | Reason |
|---|---|---|
| Package manager | pnpm 10 workspaces | Best monorepo support of the three available; accommodates `apps/mobile` without restructuring. |
| Monorepo tooling | None beyond pnpm | Turborepo adds caching value at a scale this repository has not reached. Two apps and two packages build in seconds. Revisit if build time becomes a complaint. |
| TypeScript version | 6.0.3 everywhere | Nest scaffolded on 6, Next on 5. Verified Next 16.3.4 builds clean on 6, so the workspace is aligned rather than split. |
| Test runner | vitest | What the current Nest CLI scaffolds; also used by the packages. One runner across the repository. |
| Linter | oxlint for API and packages, eslint for web | Nest scaffolds oxlint, Next requires `eslint-config-next` for its own rules. Not worth forcing one. |
| `vite-tsconfig-paths` | Removed | Vite resolves tsconfig paths natively. The plugin pinned a transitive dependency to TypeScript 5 and produced the workspace's only peer warning. |
| `@nestjs/mau` | Removed | Nest's own deployment service. Deployment is DigitalOcean per the agreed stack. |
| Dark mode | Deferred | Primary surfaces are a daylight roadside portal and an office dashboard; card identity is light. Tokens are indirected, so adding it later is not rework. |
| Zod | Deferred to item 02 | `ARCHITECTURE.md` §3 places Zod schemas in `contracts`. There are no DTOs to validate yet. |

## Notes for the next session

- `apps/api/tsconfig.json` deliberately does not extend `tsconfig.base.json`. Nest needs
  `emitDecoratorMetadata` and `strictPropertyInitialization: false`; inheriting the base's
  stricter settings breaks dependency injection.
- `pnpm typecheck` catches what `pnpm build` does not, because `nest build` uses
  `tsconfig.build.json`, which excludes test files. This already caught one real error in
  the scaffolded e2e spec.
- `apps/web/AGENTS.md` is regenerated by `next dev`. It is committed deliberately.
- The palette in `DESIGN.md` is provisional, inferred from a photograph. It must be
  replaced with values sampled from official artwork before item 06 prints anything.
